# 墨阵 · 守少主

项目的长期目标是：**让玩家通过自然语言创造、修改和组合塔防世界的规则，由受约束的内容格式和确定性 Runtime 执行。** 当前可玩原型叫“墨阵 · 守少主”，采用三国文字合成塔防玩法。

直接用浏览器打开 `index.html`。回归检查：`node test-runtime.js` 与 `node test-demo.js`。

当前“生成战局”和“AI 军师”使用本地关键词匹配与预设模板，尚未接入真实 LLM。已有内容包、有限规则、校验和无头预演，但尚未完成自然语言创作闭环。

## 产品设计主线

玩家的目标体验是：**描述创意 → 查看规则摘要 → 确认应用 → 实战观察 → 继续修改**。保存、分享和复用是长期体验的一部分。

系统按以下边界实现它：

```text
玩家表达意图
    ↓
AI 理解、澄清并生成候选内容
    ↓
结构化内容包 / 受限指令
    ↓
Schema、语义、能力与预算校验 + dry-run
    ↓
玩家确认 → 确定性 Runtime 执行 → 快照和事件 → 表现层
```

AI 提议，Runtime 裁决；战斗 tick 内不调用 AI。新内容优先组合已有能力，无法表达的新机制才由开发者增加原语。

世界模型的八个概念分别是：`Entity`（对象）、`Component`（能力与数据）、`Spatial`（空间）、`Relation`（关系）、`Rule`（触发逻辑）、`Modifier`（数值修正）、`State`（当前状态）、`Presentation`（表现）。它们是长期设计语言，当前原型只实现了其中的一部分。

## 当前原型的玩法

- 馒头随机征兵，费用从 8 起每次增加 2，最高 24；待命区最多 5 张。
- 刀、枪、弓、骑四兵种；同兵种同阶拖放合成，最高五阶。
- 初始开放 6 个阵位，抽到铲子可逐格扩展至 12 格。
- 赵+云、张+飞、黄+忠可以拖到一起，或在同行相邻时自动成将；赵云双目标、张飞范围攻击并击退、黄忠三目标。
- 我方少主初始 6 命；清完一波使敌方少主扣 2 命，默认三阵通关。敌方生命是清波进度，不是另一套对称攻防模拟。
- 击杀返还馒头，非最终波结束奖励 12 馒头；波间可以提交只影响下一波的难度军令。
- 雨天弓兵命中施加 `Frozen`（当前实际效果为减速），枪兵攻击带该状态的目标触发有限链伤；高地使射程增加 20%。

## 设计与实现的差异

以下按 2026-11-07 的仓库代码核对；“已有”仅指当前实现，不代表完整规范通过验收。

| 主题 | 文档设计 | 当前实现 / 待补内容 |
|---|---|---|
| AI 创作 | LLM 生成 JSON、最多 3 轮纠错、摘要确认、再次修改 | 摘要确认与预演已有；生成和军令仍是关键词模板，未接 LLM 和纠错循环 |
| 内容驱动 | 内容包定义塔、怪物、地图和波次 | 怪物、路径和波次读取内容包；单位创建和攻击基础数值仍取 `UNIT_DEFS`，修改包中塔定义尚不能完整改变战斗 |
| 基础玩法 | Demo v0.1 不做升级；精进版一期排除实体合并 | 当前已有升阶、拼字成将、征兵与扩格，属于额外的宿主玩法实现，尚缺对应的正式设计决策记录 |
| 规则系统 | Demo v0.1 整体延后；精进版规划通用有限规则 | 当前已有 `on_hit`、状态、两类效果和高地射程修正，是有限实现；尚无完整选择器、关系、级联队列和运行预算体系 |
| 内容校验 | Schema + 语义 + 能力校验，逐条结构化错误 | 已有部分必填、数值与效果检查；路径、引用、未知字段等未完整覆盖，也没有独立的正式 Schema 文件 |
| 确定性与结算 | 精确生命周期、整数化逻辑、稳定排序、即时死亡确认 | 固定 tick、种子随机和重复运行测试已有；仍使用浮点距离/成长公式，死亡在攻击遍历后统一清理，尚不能视为完整契约已实现 |
| 表现 | Demo 规划像素素材库与 palette swap | 当前为 Canvas 文字单位、程序绘制与 Kenney 命中特效，未实现完整像素素材选配管线 |
| dry-run | Demo 规划无塔与自动布防两种预演；精进版规划预算与详细统计 | 当前只跑固定基础布防，报告胜负、tick、基地生命、金币、击杀与漏怪；不能证明关卡平衡 |
| 版本与回放 | 精确 Runtime 版本、内容哈希、快照恢复和指令回放 | 当前有展示快照和校验和；尚无完整版本绑定、恢复与回放链路 |

另有两处文档细节需在修订基线时处理：Demo §4.6 的路径错误示例中 `[8,1]` 与 `[4,1]` 实际同处一行；精进版 §13 把死亡召唤、条件 Modifier 和预算测试列为进入 P2 前的要求，但这些能力本身安排在 P2。

## 后续设计需要收口的事项

下列是本次梳理后的建议顺序，尚不代表已经作出新的范围决策：

1. **明确宿主玩法定位。** 确认“墨阵”的征兵、合成与拼字成将是否作为正式基础玩法；补齐规则说明及其与 AI 创作的关系。
2. **统一实际可执行的内容契约。** 明确当前支持的字段、数值、效果和限制；使塔定义真正驱动战斗，并补齐结算与校验缺口。
3. **完成最小真实 AI 创作闭环。** 接入 LLM → 校验与纠错 → 预演 → 玩家确认 → 实战 → 再次修改；保留默认关卡回退。
4. **用玩家行为验证。** 沿用 Demo 的 20 条描述测试、最多 3 轮纠错后成功率 ≥80% 的工程目标，以及 3–5 名玩家中多数主动再次创作的产品目标；当前没有这两项的实测记录。
5. **按表达缺口扩展。** 根据真实创作需求增加原语，再评估多路线、召唤、完整羁绊、回放、分享和素材管线。

维护文档时：产品原则归初衷文档，通用概念归平台文档，执行语义归精进设计，当前 Demo 范围与验收归 Demo 文档；README 负责导航、实现状态和差异索引。

## 架构边界

- `runtime.js`：零 DOM / Canvas / 音频依赖的确定性规则层；内容包校验、受限军令、战斗结算和只读展示快照均在这里。
- `app.js`：展示与交互适配层；只启动 `TowerDefenseRuntime.Runtime`，画布根据快照绘制，负责拖放、音效与 UI。
- `test-runtime.js`：无浏览器规则回归；`test-demo.js`：使用模拟 DOM / Canvas 的页面适配与流程回归。

`TowerDefenseRuntime.dryRun(pack)` 可在没有 Canvas、DOM 或音频的情况下跑一局基础布防模拟，返回胜负、tick 数、基地生命、金币、击杀和漏怪指标；后续接入 LLM 时，生成内容必须先经过这一关。

当前首批可组合原语是 `on_hit` 事件、天气状态、`Frozen` 状态、`apply_status`、`chain_damage` 与 `HIGH_GROUND` 空间 Modifier。输入“雨夜/沼泽”会创建雨天内容包：弓兵命中施加 `Frozen` 减速，枪兵攻击带该状态的目标时触发有限次数的链式伤害；高地阵位则由 Runtime 的 `attack_range_milli × 1.2` Modifier 计算最终射程。

## 表现与资源

文字单位、转向后坐、弹道、命中、爆炸、音效、暂停、倍速和结算均已实现。项目没有复制参考作品的美术、音频或文案；字体来自开放许可的 Google Fonts，爆炸素材来自 Kenney Tower Defense Top-Down（CC0），许可证位于 `assets/game/LICENSE-KENNEY.txt`。
